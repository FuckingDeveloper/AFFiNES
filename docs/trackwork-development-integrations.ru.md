# TrackWork: интеграции с системами разработки

TrackWork может связывать задачи с внешними системами разработки: Git-хостингом
(GitLab) и CI-сервером (Jenkins). Связи и события отображаются в карточке
задачи в секциях Development и Activity и никогда не изменяют содержимое самой
задачи.

## Обзор архитектуры

Интеграция построена на провайдер-нейтральных абстракциях:

- **SCM-провайдер** (`ScmProvider`) — Git-хостинг: проверка подключения, список
  репозиториев, верификация вебхуков, нормализация событий (push, ветки,
  merge request).
- **CI-провайдер** (`CiProvider`) — серверы сборок: проверка подключения,
  ограниченный опрос пайплайнов, нормализация статусов.

Специфика вендора (например, `building`/`result` в Jenkins или
`object_kind: merge_request` в GitLab) остаётся внутри адаптера. В модель и API
попадают только нейтральные понятия:

- события: `commit.pushed`, `branch.updated`, `merge_request.opened/updated/merged`,
  `pipeline.{status}`;
- статусы MR: `open`, `merged`, `closed`, `draft`, `unknown`;
- статусы пайплайнов: `queued`, `running`, `success`, `failed`, `canceled`,
  `skipped`, `unstable`, `unknown`.

## Стабильные ключи задач

Каждая задача TrackWork имеет стабильный человекочитаемый ключ вида
`PREFIX-N`, например `TASK-142`. Префикс — это «ключ задач» рабочего
пространства (4 буквы, настраивается в Настройках → Профиль), номер
присваивается последовательно и не меняется.

Ссылки на задачи извлекаются из текста коммитов, названий веток, заголовков и
описаний merge request'ов, имён и описаний сборок Jenkins по шаблону
`PREFIX-N` (регистр не важен, `tw-142` эквивалентен `TW-142`).

### Смена префикса

При изменении «ключа задач» в настройках рабочего пространства все
существующие связи разработки и события активности автоматически переносятся
на новый префикс (`TASK-142` → `JIRA-142`). Правила:

- перенос выполняется только администратором;
- при конфликте с уже существующей связью запись не перезаписывается и не
  удаляется — она пропускается и остаётся под старым ключом;
- связи и события никогда не удаляются автоматически (политика
  «только добавление»).

## Подключение GitLab

GitLab — SCM-провайдер: на его вебхуки TrackWork отвечает мгновенно, а коммиты,
ветки и merge request'ы автоматически появляются в задачах.

### 1. Создайте токен доступа

В GitLab: **Settings → Access Tokens** (`/-/user_settings/personal_access_tokens`).
Минимальные права: `read_api` (или `api`, если GitLab настроен так, что
`read_api` недостаточно для `/api/v4/projects?membership=true`).

### 2. Подключите GitLab в TrackWork

Настройки → Интеграции → GitLab:

| Поле           | Значение                                                     |
| -------------- | ------------------------------------------------------------ |
| Name           | произвольное имя подключения                                 |
| GitLab URL     | например `https://gitlab.example.org` (http/https; без пути) |
| Access token   | токен из шага 1                                              |
| Webhook secret | произвольная строка, будет нужна GitLab'у на шаге 4          |

Нажмите **Connect GitLab**, затем **Test connection** — ответ должен содержать
`Connected as @имя_пользователя`.

### 3. Импортируйте репозитории

Нажмите **Load repositories** — TrackWork покажет репозитории, доступные токену.
Для каждого репозитория нажмите **Import**. Только импортированные
(включённые) репозитории участвуют в обработке вебхуков; события из остальных
репозиториев игнорируются.

### 4. Настройте вебхук в GitLab

В репозитории: **Settings → Webhooks**. URL — кнопка **Copy** на странице
подключения (вид: `https://trackwork.example.org/api/integrations/gitlab/webhook/<id>`).

Включите события:

- **Push events** — коммиты и ветки;
- **Merge request events** — открытие/обновление/слияние.

В поле **Secret token** вставьте webhook secret из шага 2.

После настройки вебхука коммит с сообщением `fix(auth): TW-142 refresh token`
автоматически появится в задаче `TW-142` в секции **Development**, а запись об
этом — в секции **Activity**.

## Подключение Jenkins

Jenkins — CI-провайдер. TrackWork опрашивает Jenkins по расписанию
пользователя (кнопка **Refresh pipelines** на странице подключения) и
отображает статусы сборок в задачах.

### 1. Создайте API-токен

В Jenkins: **Dashboard → имя пользователя → Settings → API Token** (в новых
версиях — **Add new Token**).

### 2. Подключите Jenkins в TrackWork

Настройки → Интеграции → Jenkins:

| Поле         | Значение                                            |
| ------------ | --------------------------------------------------- |
| Name         | произвольное имя подключения                        |
| Jenkins URL  | например `https://ci.example.org:8080` (http/https) |
| Username     | имя пользователя Jenkins                            |
| Access token | API-токен                                           |

Нажмите **Connect Jenkins**, затем **Test connection** — ответ должен содержать
имя Jenkins-ноды.

### 3. Обновите пайплайны

Кнопка **Refresh pipelines** опрашивает Jenkins (последние 20 сборок по каждой
задаче, не более 200 за раз) и сохраняет статусы. Повторный опрос доступен не
чаще одного раза в 30 секунд на подключение.

Сборка привязывается к задачам по ключу в имени задания или описании сборки
(например, задание `TW-142-deploy` или описание сборки `fix: TW-142`). При
смене статуса (running → success/failed/…) в задачу добавляется запись
активности `pipeline.{статус}`.

## Политика и ограничения

- **Только добавление.** Связи разработки и события активности никогда не
  изменяют и не удаляют содержимое задач. При коллизиях запись пропускается.
- **Изоляция.** Связи принадлежат рабочему пространству; доступ к ним
  проверяется на сервере (`Workspace.Read` для просмотра,
  `Workspace.Administrators.Manage` для настройки). Задача одного пространства
  не может получить связи другого.
- **Вебхуки.** Обрабатываются только события от импортированных репозиториев.
  Повторная доставка одного и того же события не создаёт дубликатов.
  Неверный секрет, отключённое или неизвестное подключение отвечают одинаково
  (404) — существование подключения не раскрывается. Частота: не более 60
  запросов в минуту на клиента; размер тела — не более 256 КБ (413).
- **Лимиты.** Не более 2000 связей и 2000 событий активности на задачу;
  при превышении новые записи пропускаются (с предупреждением в журнале).
- **Учётные данные** (токены, webhook-секреты) хранятся в базе только в
  зашифрованном виде (AES-256-GCM, ключ инстанса) и никогда не возвращаются
  клиенту.

## API

GraphQL (все операции — после аутентификации):

- `workspace(id) { developmentIntegrations }` — список подключений;
- `createDevelopmentIntegration` / `updateDevelopmentIntegration` /
  `rotateDevelopmentIntegrationCredentials` / `deleteDevelopmentIntegration` /
  `testDevelopmentIntegration` — управление подключениями (администратор);
- `developmentRepositories` / `importDevelopmentRepository` /
  `setDevelopmentRepositoryEnabled` — репозитории GitLab (администратор);
- `refreshDevelopmentPipelines` — опрос пайплайнов Jenkins (администратор);
- `trackWorkTaskDevelopment(workspaceId, taskKey)` — Development-секция задачи
  (коммиты, ветки, merge request'ы, пайплайны);
- `trackWorkActivity(workspaceId, taskKey?, first, after)` — активность с
  cursor-пагинацией;
- `migrateDevelopmentTaskKeys(workspaceId, fromPrefix, toPrefix)` — перенос
  связей при смене префикса (администратор).

REST:

- `POST /api/integrations/gitlab/webhook/:connectionId` — вебхук GitLab
  (заголовок `X-Gitlab-Token`, ответ `{ "accepted": true }`).

## Автоматизация статусов

Правила автоматизации настраиваются в Настройки → Task Tracker → Автоматизации
и применяются при открытии доски (идемпотентно, по стабильным ID событий):

- `MR opened / updated / merged` → перевести задачу на этап;
- `Pipeline success / failed / unstable` → перевести на этап или показать
  предупреждение;
- `Commit pushed` → перевести на этап.

Целевой этап выбирается по стабильному ID стадии (не по названию), правила не
привязаны к глобальным стадиям — каждая доска может иметь свои.

## Связи задач и документов

- **Документы**: панель задачи → «Документы» — привяжите любые документы
  workspace к задаче (хранятся только ID документов, контент не дублируется);
- **Ссылки (backlinks)**: панель задачи → «Ссылки» — документы, в тексте
  которых упоминается ключ задачи (вычисляется полнотекстовым поиском);
- **Подзадачи (задачи)**: панель задачи → «Подзадачи» — иерархия задач
  parent/child (создание подзадачи или связывание существующей);
- **Связи**: панель задачи → «Связи» — `blocked-by`, `relates-to`,
  `duplicates`; связи хранятся по стабильным внутренним ID задач и
  переживают переименование; родительские связи защищены от циклов.

## Ограничения текущей версии

- Опрос Jenkins выполняется по кнопке (фоновый опрос по расписанию не
  добавлен).
- Привязка сборок Jenkins к задачам выполняется по имени задания/описанию
  сборки; привязка по SHA коммита не реализована.
- Webhook GitLab обрабатывает события push и merge request; комментарии,
  теги и другие события не обрабатываются.
- Существующие записи истории задач (созданные до локализации) остаются на
  языке создания.
